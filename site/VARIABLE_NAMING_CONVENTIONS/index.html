    Legacy Notes¶

    Robot IP Address Variable¶

    History and Convention Conflict¶

    Date Discovered: October 6, 2025

    Issue: The DIMOS library (dimos-unitree) originally used GO2_IP as its convention for the robot IP address, which conflicts with the upstream go2_ros2_sdk convention of using ROBOT_IP.

    Root Cause¶

    1. go2_ros2_sdk (upstream dependency): Uses ROBOT_IP as the primary environment variable
    2. Location: go2_robot_sdk/go2_robot_sdk/presentation/go2_driver_node.py
    3. Pattern: os.getenv('ROBOT_IP', os.getenv('GO2_IP', ''))

    4. The SDK checks ROBOT_IP first, then falls back to GO2_IP for backward compatibility

    5. dimos-unitree (our fork): Originally adopted GO2_IP as its convention

    6. This created a naming conflict with the upstream SDK

    7. Led to confusing behavior where scripts checked one variable but used another

    8. shadowhound (our application): Initially followed DIMOS convention (GO2_IP)

    9. This propagated the conflict throughout our codebase
    10. Resulted in misleading warnings (e.g., "ROBOT_IP not set" when using GO2_IP)

    Resolution (October 6, 2025)¶

    Decision: Standardize on ROBOT_IP throughout the shadowhound codebase to align with the upstream go2_ros2_sdk convention.

    Rationale: - ROBOT_IP is the primary convention in the upstream SDK - Aligns with ROS2 ecosystem standards - Reduces confusion and maintenance burden - SDK already has backward compatibility fallback for GO2_IP

    Implementation: Commit 8a6e47e on feature/dimos-integration branch - Updated 12 files across the shadowhound workspace - Replaced all GO2_IP references with ROBOT_IP - External dimos-unitree SDK maintains backward compatibility

    Current State¶

    ✅ shadowhound workspace: Uses ROBOT_IP exclusively ✅ go2_ros2_sdk: Uses ROBOT_IP as primary, GO2_IP as fallback ⚠️ dimos-unitree: May still reference GO2_IP in some places (has fallback logic)

    Future Considerations¶

    If this bites us later, check:

    1. Environment Variable Priority: python # SDK checks in this order: robot_ip = os.getenv('ROBOT_IP', os.getenv('GO2_IP', ''))
    2. If both are set, ROBOT_IP takes precedence

    3. If only GO2_IP is set, SDK will still work (fallback)

    4. DIMOS Updates: If updating dimos-unitree dependency:

    5. Check if they've standardized on a different convention
    6. Verify our ROBOT_IP usage still works

    7. Look for any new environment variables related to robot connection

    8. Documentation: If seeing confusing behavior:

    9. Check if old docs/scripts are using GO2_IP
    10. Verify .env files use ROBOT_IP

    11. Confirm start.sh exports ROBOT_IP correctly

    12. Testing: When testing robot connection: ```bash # Check what's actually being used: echo "ROBOT_IP: $ROBOT_IP" echo "GO2_IP: $GO2_IP" # Should be unset in shadowhound

    # Verify SDK sees it: ros2 param get /go2_driver robot_ip ```

    1. External Scripts: If integrating third-party tools:
    2. They may expect GO2_IP (older convention)
    3. Add translation layer if needed: bash export GO2_IP=${ROBOT_IP} # For backward compat

    Lessons Learned¶

    1. Convention Alignment: When using external libraries, prefer their conventions over inventing our own
    2. Upstream First: Check upstream conventions before forking/extending
    3. Document Conflicts: When conflicts arise, document them immediately (like this!)
    4. Graceful Migration: Use fallback patterns during transitions (SDK's approach is good)
    5. Systematic Updates: Update all references at once to avoid partial migration states

    Additional Notes¶

    • The SDK's backward compatibility pattern is good practice: python value = os.getenv('NEW_NAME', os.getenv('OLD_NAME', 'default'))
    • Consider this pattern if we need to rename variables in the future
    • This conflict was subtle because both variables work - just confusing warnings
